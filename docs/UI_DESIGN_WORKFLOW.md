# UI 界面设计与开发工作流

本流程适用于新增界面、现有界面的大幅改版和一组需要统一视觉的 UI 组件。它把视觉方向、资源制作、Godot 拼装和功能开发分成连续的验收门，后续开发默认按此流程推进。

后续界面先查 [通用 UI 设计系统](UI_DESIGN_SYSTEM.md)：已有类型直接复用，差异通过组合或扩展变体解决，新类型同步登记规范与状态。通用体系 v01 已于 2026-11-06 获用户概念审核通过；已有 `UITokens`、`PaintedTheme` 和首批原生控件，具体覆盖见规范，其余按切片建设。通用控件审核不代替新界面的布局与功能审核。

## 总原则

- 每个界面先参考当前实际 UI 生成概念图，再决定视觉方向和资源拆分方式。
- 概念图必须由用户审核通过后，才进入正式抠图、分层和运行时资源整理。
- 动态文字、数值、冷却、进度、交互状态和可访问性信息始终由 Godot 绘制；概念图和图片资源不烘焙这些内容。
- 视觉资源完成后再拼装界面并接入功能。必要时可以先用代码占位验证交互，但占位状态不能记为正式 UI 完成。
- 自动回归、助手截图检查、用户视觉审核和 Android 实机审核分别记录，任何一项都不能代替另一项。

## 0. 建立界面任务卡

开始前为每个界面建立一张任务卡，先确认它要解决的功能问题和当前基线：

- 界面 ID、用途、进入和退出入口、正式场景或预览场景路径。
- 当前 UI 截图或可运行场景，记录截图日期、分辨率和是否开启触屏模式。
- 必须支持的状态：首次进入、选中、禁用、锁定、加载、空数据、错误、暂停、完成和触屏安全区。
- 设计坐标、目标比例、最小触摸尺寸、动态字段和必须复用的现有控件。
- 引用的通用控件 ID、模板、变体；若要新增类型，说明已有类型无法覆盖的具体原因。
- 视觉目标、禁止事项和验收人。用户可见文案使用简体中文，资源文件和代码沿用英文 ID。

任务卡在概念图生成前完成。没有当前 UI 基线时，先运行正式场景或共用预览入口取得基线，不直接凭代码描述生成概念图。

任务卡默认保存为 `art/validation/ui/<screen>/vNN/README.md`。可以从下面的模板开始，随着流程推进补齐状态和证据：

状态只能按以下顺序推进：`brief_ready` → `concept_review_pending` → `approved` → `assembly_in_progress` → `functional_ready` → `visual_review_pending` → `runtime_ready`。用户提出修改时回到新的概念图版本；`rejected` 版本保留记录，不覆盖旧证据。

## 1. 参考当前 UI 生成概念图

使用内置图片生成工具制作概念图，输入至少包含当前 UI 截图、[正式美术设计](ART_DIRECTION.md) 的风格锚点、界面功能说明和目标画幅。概念图用于确定构图、层级、留白、材质、色彩和视觉重点，不作为可直接导入的最终贴图。

每轮概念图保存：

- 原始 PNG 和版本号，例如 `art/concepts/ui/level_select/v01.png`。
- 提示词、参考图、生成时间、模型 / 工作流和修改原因，例如 `art/prompts/ui/level_select/v01.prompt.md`。
- 任务卡中记录本轮要解决的问题，以及没有纳入概念图的动态内容。

概念图至少要展示完整界面，而不是只画单个按钮。需要明确主要面板、导航关系、按钮排列、选中 / 锁定状态和宽屏留白。没有用户审核前，不开始正式抠图，也不把概念图复制到 `art/generated/`。

## 2. 用户审核概念图

概念图进入 `concept_review_pending` 状态后交给用户审核。审核只确认方向，不默认确认资源细节。用户反馈需要记录为具体修改项，例如面板层级、按钮位置、颜色、信息密度或角色 / 场景遮挡。

审核结果只有三种：

- `approved`：方向通过，可以进入资源整理。
- `revision_requested`：保留原版本，按反馈生成下一个版本，再次审核。
- `rejected`：停止本轮资源制作，记录原因，不覆盖旧版本。

只有明确的 `approved` 才能进入下一步。审核记录放在对应界面的验证目录或任务卡中，写明版本、日期、反馈和结论。

## 3. 抠图、分层和资源整理

审核通过后，判断界面是否需要位图资源：

- 需要透明对象、面板材质、图标或装饰纹理时，使用现有 `extract-layered-psd` 流程或等价的可复核拆层流程。
- 纯布局、文字、进度、按钮状态和简单几何优先直接用 Godot `Control`、主题和绘制节点实现。
- 不把整张概念图当作运行时 UI 背景，也不把动态文字、数字、冷却或锁定条件烘焙进图片。

资源整理必须保留原图、PSD / 分层结果、图层清单、透明边界、尺寸、来源和检查报告。候选资源先放在 `art/layered/ui/<screen>/vNN/`，只有通过透明边缘、缩放、图集边界和实际画面对照后，才复制到 `art/generated/ui/<screen>/`。

候选资源默认标记为 `runtime_ready: false`。结构校验通过只说明文件可读、图层和导出一致，不代表与概念图或当前 UI 的视觉一致。

## 4. 拼装 Godot UI

资源整理完成后，在正式界面或共用预览入口中拼装 UI：

1. 先按 1280×720 设计坐标放置面板、按钮、图标和动态字段。
2. 使用 `ScreenLayout` 计算安全区，检查 1280×720、宽屏和触屏尺寸。
3. 让图片负责材质和装饰，让 Godot 节点负责文字、数值、状态、动画和交互反馈。
4. 用统一主题、按钮状态和间距规则复用已有控件；只有节点结构或渲染环境确实不同才新增预览场景。
5. 在功能接入前完成静态拼装截图，确认层级、边缘、缩放和留白与已审核概念图一致。

拼装阶段状态为 `assembly_in_progress`。若资源仍是候选图层，可以用占位图完成布局验证，但必须在任务卡中标记占位，不得写成视觉完成。

## 5. 接入功能

在 UI 拼装稳定后接入功能逻辑。功能开发至少覆盖：

- 鼠标 / 键盘 / 触屏的同一语义，短点按、按住、松开、多指和失焦清理。
- 进入、返回、暂停、重试、失败、完成、加载失败和重复点击。
- 锁定、选中、禁用、冷却、空数据和保存失败等状态。
- 动态数据来自标准运行时接口，UI 不直接修改存档、经济或当局快照。
- 功能所需的资源和文案都有稳定 ID，界面不扫描文件夹自行决定解锁或业务规则。

功能接入完成后状态为 `functional_ready`，这只表示行为可用，不等于视觉验收完成。

## 6. 分层验收

每个界面至少记录以下四类结果：

1. **自动行为回归**：入口、状态切换、输入、数据绑定、返回 / 重试和存档边界。
2. **助手截图检查**：目标分辨率、宽屏、安全区、透明边缘、层级和文字裁切。
3. **用户视觉审核**：概念方向、材质、比例、信息层级和整体观感。
4. **Android 实机审核**：触摸命中、手指遮挡、系统安全区、帧率和缩放手感。

截图检查通过后状态为 `visual_review_pending`；用户视觉审核通过后才可标记 `runtime_ready: true`。Android 未验收时，文档必须保留“桌面已通过、Android 待验收”的边界。

## 7. 交付与后续修改

界面完成时，任务卡至少包含：概念图版本、用户审核结论、资源清单、Godot 入口、自动测试命令、截图路径、用户 / Android 验收状态和仍待处理的问题。

后续改版从新的概念图版本开始，例如 `v02`，不覆盖已审核的概念图、PSD、候选资源或验证报告。功能小修可以直接修改代码，但只要改变布局、材质、信息层级或交互结构，就必须回到概念审核门。

推荐目录结构：

```text
art/
├── concepts/ui/<screen>/vNN.png
├── prompts/ui/<screen>/vNN.prompt.md
├── workbench/ui/<screen>/vNN/       # 忽略的原始工作文件
├── layered/ui/<screen>/vNN/         # PSD、透明图层、清单和候选报告
├── generated/ui/<screen>/vNN/       # 已接入运行时的资源
└── validation/ui/<screen>/vNN/      # 截图、回归摘要和审核记录
```

详细的 PSD 拆层命令、结构检查和候选资源规则继续以 [美术流水线](ART_PIPELINE.md) 为准；本文件补充的是每个 UI 界面必须经过的产品设计和审核顺序。
